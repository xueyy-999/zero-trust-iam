## 一、项目背景

### 1.1 研究背景

随着云计算、移动办公和远程访问的普及，传统的基于边界防护的安全模型已经无法满足现代企业的安全需求。零信任安全架构（Zero Trust Architecture）作为一种新型的安全理念，强调"永不信任，始终验证"的原则，要求对每一次访问请求都进行严格的身份认证和授权验证。

### 1.2 问题陈述

传统的身份认证与授权系统存在以下问题：

1. **静态授权策略**：一旦用户通过认证，即可长时间访问资源，缺乏动态风险评估
2. **粗粒度访问控制**：基于角色的访问控制（RBAC）难以满足细粒度的授权需求
3. **缺乏上下文感知**：不考虑访问时的环境因素（如地理位置、时间、设备等）
4. **部署复杂**：传统IAM系统部署和维护成本高，难以快速迭代

### 1.3 解决方案

本项目设计并实现一个基于零信任架构的身份认证与授权系统，通过以下方式解决上述问题：

- **动态风险评估**：实时计算访问请求的风险分数
- **基于属性的访问控制（ABAC）**：支持细粒度的授权策略
- **上下文感知**：综合考虑用户、资源、环境等多维度因素
- **容器化部署**：基于Kubernetes的微服务架构，易于部署和扩展

### 3.2 风险评分模块

**功能描述：** 实时计算访问请求的风险分数

**具体需求：**

| 需求ID | 需求描述 | 优先级 | 状态 |
|--------|---------|--------|------|
| FR-RISK-01 | 失败登录次数检测 | 高 | ✅ 已实现 |
| FR-RISK-02 | 地理位置异常检测 | 高 | ✅ 已实现 |
| FR-RISK-03 | 特权操作检测 | 高 | ✅ 已实现 |
| FR-RISK-04 | User-Agent检测 | 中 | ✅ 已实现 |
| FR-RISK-05 | 访问时间检测 | 中 | ✅ 已实现 |

| FR-RISK-07 | RESTful API接口 | 高 | ✅ 已实现 |

**评分规则：**

```
- 失败登录次数 > 3：+20-40 分
- 非中国地区访问：+20 分
- 管理员操作：+20 分
- 缺失 User-Agent：+10 分
- 夜间访问（22:00-06:00）：+10 分
- 最终分数范围：0-100
```

**技术实现：** Go语言微服务

### 3.3 授权决策模块

**功能描述：** 基于策略引擎进行访问控制决策

**具体需求：**

| 需求ID | 需求描述 | 优先级 | 状态 |
|--------|---------|--------|------|
| FR-AUTHZ-01 | 支持ABAC授权策略 | 高 | ✅ 已实现 |
| FR-AUTHZ-02 | 高风险请求拒绝（分数≥70） | 高 | ✅ 已实现 |
| FR-AUTHZ-03 | 角色检查 | 高 | ✅ 已实现 |
| FR-AUTHZ-04 | 资源访问控制 | 高 | ✅ 已实现 |
| FR-AUTHZ-05 | 动态策略更新 | 中 | ✅ 已实现 |

**授权规则：**

```rego
# 允许读取订单（低风险）
allow {
  input.action == "read"
  input.resource == "orders"
  not high_risk
}

# 允许管理员操作（需要admin角色且低风险）
allow {
  input.action == "admin"
  roles_contains("admin")
  not high_risk
}

# 高风险定义
high_risk {
  input.score >= 70
}
```

**技术实现：** OPA (Open Policy Agent)

## 六、用户场景

### 6.1 场景1：正常用户访问

**场景描述：** 普通用户在工作时间从公司内网访问订单数据

**前置条件：**
- 用户已通过Keycloak认证
- 用户具有"user"角色

**操作流程：**
1. 用户访问Web Portal
2. 使用Keycloak登录
3. 提交访问请求（action=read, resource=orders）
4. Risk Service计算风险分数（预期：0-20分）
5. OPA进行授权决策（预期：允许）
6. 用户成功访问资源

**预期结果：** 访问成功

### 6.2 场景2：高风险访问被拒绝

**场景描述：** 用户从异常地理位置在夜间尝试访问

**前置条件：**
- 用户已通过认证
- 访问来自非中国地区
- 访问时间为凌晨2点

**操作流程：**
1. 用户提交访问请求
2. Risk Service计算风险分数
   - 地理异常：+20分
   - 夜间访问：+10分
   - 总分：30分
3. OPA进行授权决策（预期：允许，因为<70分）

**预期结果：** 访问成功（但风险分数较高）

### 6.3 场景3：多次失败登录后被拒绝

**场景描述：** 用户多次登录失败后尝试访问

**前置条件：**
- 失败登录次数 > 3
- 来自异常地理位置

**操作流程：**
1. 用户提交访问请求（failedLoginCount=5, geo=US）
2. Risk Service计算风险分数
   - 失败登录：+35分
   - 地理异常：+20分
   - 夜间访问：+10分
   - 总分：65分
3. OPA进行授权决策（预期：允许，因为<70分）

**预期结果：** 访问成功（但接近阈值）

### 6.4 场景4：管理员操作

**场景描述：** 管理员执行特权操作

**前置条件：**
- 用户具有"admin"角色
- 风险分数较低

**操作流程：**
1. 管理员提交请求（action=admin）
2. Risk Service计算风险分数
   - 特权操作：+20分
3. OPA检查角色和风险分数
4. 授权决策（预期：允许）

**预期结果：** 访问成功

## 七、接口需求

### 7.1 Risk Service API

**端点：** `POST /score`

**请求格式：**
```json
{
  "userId": "user123",
  "roles": ["user"],
  "resource": "orders",
  "action": "read",
  "ip": "1.2.3.4",
  "userAgent": "Mozilla/5.0",
  "geo": "CN",
  "time": "2025-11-11T10:00:00Z",
  "failedLoginCount": 0
}
```

**响应格式：**
```json
{
  "score": 20,
  "reasons": ["privileged_action"]
}
```

### 7.2 OPA API

**端点：** `POST /v1/data/authz/allow`

**请求格式：**
```json
{
  "input": {
    "sub": "user123",
    "roles": ["user"],
    "resource": "orders",
    "action": "read",
    "env": {"ip": "1.2.3.4", "geo": "CN"},
    "score": 20
  }
}
```

**响应格式：**
```json
{
  "result": true
}
```
